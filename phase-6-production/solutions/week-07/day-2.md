## Exercise 1 — Schedule trigger

```yaml
on:
  push:
    branches: [main, "feature/**"]
  pull_request:
    branches: [main]
  schedule:
    - cron: "0 2 * * *"   # 02:00 UTC nightly
```

**Which jobs should run on schedule vs. push?**

On `push` / `pull_request`: the full pipeline (lint, test, build, scan, deploy) — validating the specific change.

On `schedule`:
- Lint and test against `main` — catches new CVEs in transitive deps without a code change.
- Dependency audit (`pip-audit`) — new vulnerability databases are published daily.
- Integration tests — run against the live staging environment to detect environment drift.
- **Skip build/deploy** on schedule unless you specifically want a nightly release.

Condition the build job:
```yaml
build:
  if: github.event_name != 'schedule'
  needs: [test, audit]
```

## Exercise 2 — 2×2 matrix (Python version × OS)

```yaml
strategy:
  matrix:
    python-version: ["3.11", "3.12"]
    os: ["ubuntu-latest", "ubuntu-22.04"]
  fail-fast: false

runs-on: ${{ matrix.os }}
```

This produces four jobs:
- `ubuntu-latest` + `3.11`
- `ubuntu-latest` + `3.12`
- `ubuntu-22.04` + `3.11`
- `ubuntu-22.04` + `3.12`

Update the cache key to include both dimensions:
```yaml
key: ${{ matrix.os }}-py${{ matrix.python-version }}-pip-${{ hashFiles('requirements*.txt') }}
```

## Exercise 3 — hashFiles for pyproject.toml vs requirements.txt

**`hashFiles('**/requirements*.txt')`**: hash changes only when a `requirements.txt` file changes. Fast. Works when you use pinned requirements files.

**`hashFiles('pyproject.toml')`**: hash changes when `pyproject.toml` changes (which may be less often than actual dependency resolution changes). Riskier: if you use flexible version specs in `pyproject.toml` (`fastapi>=0.100`), the cache key stays the same even as newer package versions are installed.

**Prefer `requirements*.txt`** when you have locked files generated by `pip-compile` or `uv pip compile`. The hash reflects the exact pinned versions. Use `pyproject.toml` only if it is your canonical lock file (rare in Python).

## Exercise 4 — workflow_dispatch with inputs + dry_run

```yaml
on:
  workflow_dispatch:
    inputs:
      environment:
        description: "Target environment"
        required: true
        type: choice
        options: [dev, staging, prod]
      dry_run:
        description: "Dry run (skip actual deployment)"
        required: false
        type: boolean
        default: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    steps:
      - uses: actions/checkout@v4

      - name: Deploy
        run: |
          if [ "${{ inputs.dry_run }}" = "true" ]; then
            echo "DRY RUN — would deploy to ${{ inputs.environment }}"
            echo "Image: ${{ github.sha }}"
          else
            echo "Deploying to ${{ inputs.environment }}"
            # actual deploy command here
          fi
```

## Exercise 5 — GITHUB_TOKEN safety vs. rotation policy for custom secrets

**`secrets.GITHUB_TOKEN`** is auto-generated by GitHub Actions for each workflow run. It:
- Has a short TTL (expires when the job finishes or after 24 hours max).
- Has scoped permissions defined by the `permissions:` block in the workflow.
- Is never stored anywhere by the user — no risk of human error exposing it.
- Cannot be used outside the context of the run it was issued for.

**A manually added secret (`MY_API_KEY`):**
- Is a long-lived credential that persists until explicitly rotated.
- If leaked (via a log line, a `--verbose` flag accidentally left on, or a compromised runner), it remains valid indefinitely.
- Must have a rotation policy: automatic rotation every 30–90 days, alerts on first use from unexpected IP, monitoring for unexpected API calls.
- Should be scoped to the minimum permissions needed (e.g., a separate service account key, not a personal key with broad access).

For production: prefer OIDC over any long-lived key. If you must use a static key, store it in a secrets manager (AWS Secrets Manager, HashiCorp Vault) and rotate on a schedule; the GitHub Secret value is just the current version.
