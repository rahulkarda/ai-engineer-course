# Solutions — Week 10 · Day 6 (Saturday): Build Day Notes

## Guidance for self-review of your Day 6 deliverables

Day 6 is a production day, not an exercise day. The following notes help you evaluate your own work before submitting on Day 7.

---

## Story bank self-check rubric

For each STAR entry you wrote, apply this per-story test:

| Question | If NO → what to fix |
|----------|---------------------|
| Could a stranger understand the stakes in the first 3 sentences? | Rewrite Situation — add stakes, remove assumed context |
| Does the Task sentence start with "I" not "we"? | Reframe to a specific personal responsibility |
| Does each Action bullet start with an active past-tense verb? | Replace passive constructions ("was involved in," "helped with") with specific actions |
| Does the Result contain a number? | Add a metric — even approximate ones ("cut review time from ~3 days to <4 hours") |
| Does the Result contain a learning sentence? | Add one sentence starting "I learned..." or "This changed how I..." |
| Is the spoken version ≤ 2.5 minutes? | Read it aloud and time it. Cut from the Situation first, then Action |

**Common issues found in self-review:**

1. **Situation too long.** Most people over-explain context. Test: if you remove the last sentence of your Situation, does the story still make sense? If yes, remove it.

2. **Action bullets are still outcomes, not actions.** "The team shipped successfully" is a result, not an action. "Wrote the rollback procedure and ran a dry-run 48 hours before launch" is an action.

3. **Result is only positive.** Strong result sections acknowledge what you would do differently, even for successful stories. "It worked, and if I did it again I'd involve the security team two weeks earlier instead of one" is more credible than "it was a great outcome."

## Design doc self-check rubric

| Section | Common issue | Fix |
|---------|-------------|-----|
| Problem | Cost of inaction is qualitative ("things are slow") | Add a number: time, money, incidents, user churn |
| Goals | Goals are activity-based ("we will build X") | Rewrite as outcomes ("feature staleness will be ≤ 30s") |
| Non-goals | Non-goals are obvious ("we are not building a new product") | Non-goals should surprise the reader — name things people might reasonably expect |
| Alternatives | One alternative is a strawman (clearly unworkable) | Replace with a real alternative that required actual analysis to reject |
| Open questions | Owner is "the team" | Name a specific person |
| Success metrics | Metric listed with no measurement method | Add: named dashboard, measurement frequency, who checks it |

## Dual-use reframe technique

If you struggle to write the dual-use reframe, use this fill-in-the-blank:

> "I want to tell you about a time I [ACTION THAT FOREGROUNDS SECONDARY COMPETENCY], which led to [OUTCOME FROM THE STORY]."

Example for a story whose primary is Impact and secondary is Leadership:  
> Primary opening: "I want to tell you about a project where I cut our inference cost by 60%."  
> Secondary (leadership) opening: "I want to tell you about a time I convinced my team to scrap a nearly-finished approach and rebuild it — and why that was the right call."

The outcome stays the same. The opening verb ("convinced," "rebuilt") primes the interviewer's competency antenna.
