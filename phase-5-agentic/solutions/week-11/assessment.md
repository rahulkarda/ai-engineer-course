## Conceptual answers

**1. What does `Agent[DepsType, ResultType]` enforce?**

The generic parameters enforce two things at the type-checker level:
- `DepsType`: the type of the object that must be passed as `deps=` at call time. If you pass the wrong type, mypy/pyright flags it before runtime.
- `ResultType`: the type of `RunResult.data`. If you access a field that doesn't exist on `ResultType`, the type checker catches it.

This is preferable to an untyped `Agent` because errors are caught at write time, not at `KeyError`/`AttributeError` runtime. It also documents the agent's contract.

**2. `@agent.tool` vs `@agent.tool_plain`**

`@agent.tool_plain` is a pure function — no context. Use it when the tool only needs its explicit arguments.
`@agent.tool` receives `RunContext[DepsType]` as the first parameter, giving access to `ctx.deps`, `ctx.usage`, and `ctx.retry`. You must use `@agent.tool` when you need to read injected dependencies or call `raise ModelRetry` with context-aware logic.

**3. What happens when the model sends `{"count": "five"}` for an `int` field?**

Pydantic AI validates tool call arguments through Pydantic before calling the function. `"five"` cannot be coerced to `int`, so a `ValidationError` is raised. Pydantic AI converts this to an error message that is sent back to the model, which can then retry with a corrected value. The tool function is never called with invalid arguments.

**4. Why does step count matter?**

More tool calls = more tokens = higher cost + latency. Agent B's 6-step path is fragile — on slightly different inputs it may spiral to 10+ calls. Two metrics that catch this:
- `step_count_delta`: actual steps minus golden steps (should be near 0)
- `avg_step_delta` across eval suite: shows systemic drift

**5. Golden trajectory lifecycle**

1. **Capture**: Run the agent with known inputs, record all tool calls and the output.
2. **Review**: A human (or senior engineer) inspects the trajectory — is this the right path?
3. **Store**: Serialise to `tests/golden/<case_id>.json` and set `approved: true`.
4. **Gate**: CI runs the eval suite, compares actual trajectories to goldens, fails if drift exceeds threshold.
5. **Update**: When behaviour intentionally changes (new tool added, prompt revised), re-capture and re-review.

**6. When is an LLM judge more appropriate?**

When the expected output is open-ended and semantic — no exact string can represent "correct". Example: evaluating a code review agent's `recommendation` field. "The function is overly complex and should be refactored into smaller units" and "Consider splitting this function to reduce complexity" both deserve full marks, but exact-match would fail the second.

Use LLM judge when:
- Multiple valid phrasings exist for a correct answer
- Quality is multi-dimensional (accuracy + completeness + style)
- Safety/policy adherence requires semantic understanding

**7. Traces, spans, and agent.run()**

One `agent.run()` call = one trace. A trace is the root container. Inside it, every step is a span: the initial model call, each tool call, each tool return, the final model call. Spans have parent-child relationships — a tool call span's parent is the model call span that triggered it.

Parent-child structure tells you: which model call caused which tool call, and how long each phase took relative to its parent. Without it, you have a flat list of events with no causal structure.

**8. `result.usage()` fields**

Returns a `Usage` object. The two main fields:
- `request_tokens` (input tokens sent to the model)
- `response_tokens` (output tokens generated by the model)

Cost = `(request_tokens / 1_000_000) * input_price + (response_tokens / 1_000_000) * output_price`

**9. `ModelRetry` vs `ValueError`**

`ModelRetry(message)` sends `message` back to the model and asks it to try again (up to the retry limit). The model sees the error and can adjust its next tool call.

`ValueError` (or any other exception) propagates as a run error — it does not become a model message. The agent fails immediately without the model getting a chance to correct.

Use `ModelRetry` for recoverable errors where the model might fix the call (bad argument, missing required data). Use `ValueError` for programming errors that should never happen at runtime.

**10. Pydantic AI output validation improvements**

1. **Automatic JSON parsing and type coercion**: `result.data` is already a validated `ResultType` instance. No `json.loads()`, no `dict["field"]` access — just `result.data.field`. If the model returns malformed JSON, Pydantic AI retries automatically.

2. **Schema enforcement**: If the model returns `{"severity": "critical"}` but `severity` has `Field(pattern="^(low|medium|high)$")`, validation fails and the model is asked to retry with a valid value. Manual `json.loads` would silently accept the invalid value.

```python
# src/agents/summary_agent.py
from __future__ import annotations

import logging
import os
from dataclasses import dataclass
from typing import Annotated

from pydantic import BaseModel, Field
from pydantic_ai import Agent, RunContext

logger = logging.getLogger(__name__)


class SummaryResult(BaseModel):
    summary: str
    word_count: int
    language_detected: str


@dataclass
class SummaryDeps:
    max_words: int
    language: str


summary_agent: Agent[SummaryDeps, SummaryResult] = Agent(
    model="anthropic:claude-sonnet-5-5",
    deps_type=SummaryDeps,
    result_type=SummaryResult,
    system_prompt="You are a concise summariser. Use tools to analyse and truncate text.",
)


@summary_agent.tool_plain
def count_words(text: str) -> int:
    """Count the number of words in a text string.

    Args:
        text: Text to count words in.
    """
    return len(text.split())


@summary_agent.tool
def detect_language(ctx: RunContext[SummaryDeps], text: str) -> str:
    """Detect the language of the text. Returns the configured target language.

    Args:
        text: Text whose language is to be detected.
    """
    return ctx.deps.language


@summary_agent.tool_plain
def truncate(text: str, max_words: int) -> str:
    """Return the first max_words words of the text.

    Args:
        text: Source text.
        max_words: Maximum number of words to return.
    """
    words = text.split()
    return " ".join(words[:max_words])


# ── Eval helpers ──────────────────────────────────────────────────────────────
def score_summary(result: SummaryResult, expected_word_count: int) -> bool:
    return result.word_count <= expected_word_count
```

    result = SummaryResult(summary="short text", word_count=2, language_detected="English")

    result = SummaryResult(summary="too long text", word_count=10, language_detected="English")
    assert score_summary(result, 5) is False
