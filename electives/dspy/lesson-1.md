## Concept

### The problem with prompt strings

Hand-written prompts are brittle. You spend hours engineering a string, it works for
your dev examples, then degrades on edge cases in production. When you switch models,
you start over. When your data distribution shifts, you debug strings instead of logic.

DSPy's thesis: **prompts are implementation details, not the program**. The program is
the *structure* — what inputs flow into what outputs through what reasoning steps.
Separating structure from text lets a compiler find better text than you would by hand.

### Programs over prompts

In conventional LLM code:

```python
# Conventional — structure and text tangled together
prompt = f"""You are a helpful assistant.
Given the question: {question}
And context: {context}
Answer concisely:"""
response = client.messages.create(model="...", messages=[{"role": "user", "content": prompt}])
```

In DSPy:

```python
import dspy

class AnswerQuestion(dspy.Signature):
    """Answer a question given supporting context."""
    context: str = dspy.InputField()
    question: str = dspy.InputField()
    answer: str = dspy.OutputField()

qa = dspy.Predict(AnswerQuestion)
result = qa(context="...", question="...")
```

The prompt text is generated by DSPy. You never write it. The optimizer can rewrite it
to maximize your metric.

### The DSPy stack

```
Your metric (what "good" means)
        ↓
  Optimizer (finds best prompts + examples)
        ↓
  Program (Signatures + Modules)
        ↓
  LM backend (Anthropic, OpenAI, etc.)
```

## How it works internally

### Signatures

A `dspy.Signature` is a Python class that declares:

- **InputFields** — data flowing *in* to the LM call
- **OutputFields** — structured data the LM must produce

DSPy serializes these into a prompt template at runtime:

```
Given the fields `context`, `question`, produce the fields `answer`.

---

Follow the following format.

Context: ${context}
Question: ${question}
Answer: ${answer}
```

The docstring on the Signature becomes the task instruction. You don't write the
boilerplate; DSPy generates it and can *replace* the instruction during optimization.

### Field descriptions

You can add `desc=` to guide the model without hard-coding the full instruction:

```python
class Classify(dspy.Signature):
    """Classify the sentiment of a product review."""
    review: str = dspy.InputField(desc="raw review text")
    sentiment: str = dspy.OutputField(desc="one of: positive, negative, neutral")
```

### LM configuration

DSPy wraps LM providers. Configure once at module level:

```python
import dspy
import os

lm = dspy.LM(
    model="anthropic/claude-haiku-5-5",
    api_key=os.getenv("ANTHROPIC_API_KEY"),
)
dspy.configure(lm=lm)
```

Model IDs for Anthropic through DSPy use the `anthropic/` prefix followed by the
standard model name.

## Worked example

```python
"""lesson1_signatures.py — First DSPy program."""
import logging
import os

import dspy

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)


def build_lm() -> dspy.LM:
    """Create and configure the language model."""
    api_key = os.getenv("ANTHROPIC_API_KEY")
    if not api_key:
        raise EnvironmentError("ANTHROPIC_API_KEY not set")
    return dspy.LM(
        model="anthropic/claude-haiku-5-5",
        api_key=api_key,
        max_tokens=512,
    )


class SummarizeText(dspy.Signature):
    """Produce a one-sentence summary of the input text."""

    text: str = dspy.InputField(desc="source text to summarize")
    summary: str = dspy.OutputField(desc="one sentence, ≤ 25 words")


class ExtractKeywords(dspy.Signature):
    """Extract the three most important keywords from a text."""

    text: str = dspy.InputField()
    keywords: str = dspy.OutputField(
        desc="comma-separated list of exactly three keywords"
    )


def run_demo(text: str) -> None:
    lm = build_lm()
    dspy.configure(lm=lm)

    summarizer = dspy.Predict(SummarizeText)
    extractor = dspy.Predict(ExtractKeywords)

    summary_result = summarizer(text=text)
    logger.info("Summary: %s", summary_result.summary)

    kw_result = extractor(text=text)
    logger.info("Keywords: %s", kw_result.keywords)


if __name__ == "__main__":
    sample = (
        "DSPy is a framework for algorithmically optimizing LM prompts and weights. "
        "It replaces hand-crafted prompt strings with composable, typed modules "
        "whose instructions are tuned automatically by an optimizer."
    )
    run_demo(sample)
```

Run it:

```bash
ANTHROPIC_API_KEY=<your-key> python lesson1_signatures.py
```

Expected output (values vary by model):

```
INFO:__main__:Summary: DSPy automates prompt optimization through composable typed modules.
INFO:__main__:Keywords: optimization, modules, prompts
```

## Exercises

1. **Inline signature** — DSPy also accepts a shorthand string syntax:
   `dspy.Predict("question -> answer")`. Rewrite `SummarizeText` using the string
   shorthand and verify it produces the same structure.

2. **Multi-output signature** — Create a `AnalyzeReview` signature that takes a
   `review: str` and outputs both `sentiment: str` (positive/negative/neutral) and
   `confidence: str` (high/medium/low). Wire it to `dspy.Predict` and call it.

3. **Field descriptions matter** — Run `ExtractKeywords` without the `desc=` on the
   output field. Does the output format degrade? Add a strict description and observe
   the difference. (Use `dspy.inspect_history(n=2)` to see the raw prompts sent.)

4. **Error handling** — Wrap the `run_demo` function so it raises a clear
   `RuntimeError` with the model name and the failed field when `ANTHROPIC_API_KEY` is
   missing, rather than an uncontrolled exception deep inside DSPy.

5. **Unit test** — Write a pytest test for `AnalyzeReview` that patches the DSPy LM
   call (mock `dspy.Predict.__call__`) and asserts the output fields are present. Do
   not make a real API call.
